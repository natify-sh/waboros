# Components without fusion: our own component front end as a wasm module

A note from the maintainer's discussion, for the orchestrator. It extends ROADMAP open question 11
(components on the fly through meld). **Nothing here is approved for implementation.** The current
plan stays: meld for now. This note records the alternative so that the runtime keeps the door open
for it.

## How others load components

* **Wasmtime does not fuse.** At load it splits a component into its embedded **core modules**, an
  **instantiation plan** (which instance to create in which order, how imports and exports connect),
  and **adapters** for calls between components: the canonical ABI's lift/lower, copying strings
  and lists between linear memories, string transcoding. The adapters are generated by FACT,
  "Wasmtime's Fused Adapter Compiler of Trampolines", which "will generate a core wasm binary which
  contains the adapters" ([wasmtime_environ::fact](https://docs.wasmtime.dev/api/wasmtime_environ/fact/index.html)); Cranelift then
  compiles that core wasm like any other. The component model is a front end over core wasm, not a
  second execution engine.
* **jco** (Bytecode Alliance) does the same for JavaScript: core modules plus JS glue for the
  canonical ABI. Its transpiler ships to JS as a wasm component: `js-component-bindgen-component`,
  "WebAssembly component that (when transpiled) makes `js-component-bindgen` available in JS `jco`"
  ([README](https://github.com/bytecodealliance/jco)). This is the closest precedent for "a
  universal wasm module that takes components apart".
* **meld** (our current plan) fuses statically: everything, adapters included, into **one** core
  module with multiple memories. It is already on PyPI as `meld-cli` (native wheels, 0.66.0); a wasm
  build has been requested (pulseengine/meld#539).

## The alternative: a component front end of our own, shipped as wasm

The same pattern as the micro-compilers ([MICRO-COMPILERS.md](MICRO-COMPILERS.md)): one wasm module,
written in a language that compiles to wasm, run by waboros itself. Contract, bytes in, bytes out:

```
input:  component bytes
output: 1. the embedded core modules, unchanged
        2. one generated core module with the adapters (FACT's role)
        3. an instantiation plan: a small versioned format (instances in order, each import
           bound to an export of an earlier instance, a host import, or an adapter)
```

The runtime compiles every core module the usual way (JIT or `pyc`, cached separately), then
creates and links the instances in one Store following the plan. Multi-memory and linking several
instances exist already.

### What it gives over fusion

* **No fusion step**: no rewriting and renumbering of large modules at load; each core module is
  cached by its own hash, and a component that shares a module with another reuses it.
* **Closer to the oracle**: separate instances and separate memories, as in Wasmtime, so trap
  frames, limits and memory growth behave per instance as Wasmtime reports them.
* **No external dependency** in the long run.

### Why not now

* **Size.** Component parsing, adapter generation (lift/lower of every type, string transcoding
  between UTF-8/UTF-16/latin1, list copies with alignment), resources and handle tables, the
  instantiation plan: in Wasmtime this is in the order of ten thousand lines of Rust, not hundreds.
* **A moving target.** WASI p3 brings async: `stream`, `future`, task switching, backpressure.
  Following it is expensive; meld and Wasmtime do that work today.
* **Part of the work is needed anyway.** Lifting component values to Python objects at the host
  boundary (and lowering them back) is ours in every variant (ROADMAP q11: "Python values need our own
  canonical-ABI lift at the boundary"). The front end adds the component-to-component adapters and
  the plan, not the whole canonical ABI.

## Rule for now (so the door stays open)

When component loading is built (phase 6), keep "component -> core modules" behind **one narrow
internal interface**, whose result is "core modules + plan":

* the meld path returns one fused module and a trivial plan (one instance);
* a future front end returns several modules, the adapter module and a real plan.

The runtime instantiates from the plan in both cases. The front end can then be written later as one
more wasm module next to the micro-compilers and checked differentially against Wasmtime (component
run results) and against meld (same outputs for the same component).

## Open questions for later

1. Language of the front end: Rust (closest to the references and `wasm-tools`' parser crates, but
   watch determinism), Zig or C (smaller modules).
2. Reuse `wasmparser` / `wit-parser` compiled to wasm as libraries inside it, or write the parser too
   (the "read others, write our own" rule covers copying code, not using a library as a dependency).
3. Async (p3): implement in the plan and the runtime, or leave to meld until it settles.
