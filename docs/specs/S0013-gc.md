# S0013 Garbage collection (Wasm GC) on pyc, jit-x86_64 and jit-aarch64

## Summary
The GC proposal of Wasm 3.0: recursive type groups, declared subtyping, struct and array types
with packed fields, the abstract heap types `any`, `eq`, `i31`, `struct`, `array`, `none`,
`nofunc`, `noextern`, the 31 instructions of the 0xFB prefix, casts, and GC constant
expressions. It is a Wasmtime 50 default (WASM-PROPOSALS.md), so it is a parity item on every
target (D25). It touches six contracts: the front end's type representation (shared by every
target), the context ABI and the trampolines (S0003, S0004), the artifact format (a stack-map
section, ARTIFACT.md part 2), the trap codes (ARTIFACT.md part 3), the spec runner's engine
interface (S0001), and the JIT's lowering under D39 and S0011. That is why it needs a spec.

**Typed function references are done** (WASM-PROPOSALS.md; `call_ref`, `return_call_ref`,
`br_on_null`, `br_on_non_null`, `ref.as_non_null`, `local_init` pass on all three targets). This
spec builds on them and changes only their type identity ("Canonical keys" below).

**The pinned suite** (`test/core` at the S0001 commit):
* `gc/`: 17 files, **798 commands**: 98 `module`, 453 `assert_return`, 128 `assert_trap`, 77
  `assert_invalid`, 20 `action`, 12 `register`, 8 `assert_unlinkable`, 2 `assert_malformed`.
  The largest are `type-subtyping` 131, `ref_eq` 89, `i31` 73, `ref_test` 71, `array` 54.
* **Every one of the 78 expected failures** of `pyc`, `jit-x86_64` and `jit-aarch64` needs GC:
  * core: `ref_null.wast` 34 (`anyref`, 0x6E), `type-rec.wast` 17, `type-equivalence.wast` 12,
    `type-canon.wast` 2 (rec groups), `linking.wast:112` 1 (an immutable `(ref func)` global
    imported as `(ref null func)`: import matching with subtyping);
  * `exceptions/cast.wast` 5 (`ref.test`, `ref.cast`) and `exceptions/tag.wast` 3 (rec groups);
  * `bulk-memory/table_init.wast` 2 and `memory64/table_init64.wast` 2 (rec groups).
* **The oracle** (`xfail/wasmtime.txt`, 320 lines) fails 318 GC commands: 262 because wasmtime-py
  aborts the process on a concrete reference type in a signature, 55 on trap texts the runner
  does not map (`cast failure` 30, `out of bounds array access` 18, `null array reference` 7).
* Result forms the runner does not know yet: `i31ref`, `structref`, `arrayref`, `eqref` (any
  non-null value of that kind), `anyref N` (the host value N internalized), and `externref`
  without a value (any non-null externref). Arguments: `(ref.host N)` for an `anyref` parameter.

**Progress** (2026-11-11): steps 0 (runner and oracle), 1a (types: read, validate, link;
`frontend.types.key` as a SHA-256 digest; the review fixes), 1b (0xFB and `ref.eq` decoding and
validation, allocating constant expressions, reference masks at call sites) and 2 (`pyc` executes
GC and claims `gc`: all 798 `gc/` commands, 797 pass and 1 skipped as on Wasmtime, no expected
failure left in `xfail/pyc.txt`) are done; steps 0, 1a and 1b are reviewed; **next is step 3a**
(safepoints for every module, both JITs). Both JITs still refuse a module with GC types or
instructions ("GC types", `mod["gc"]`; such a module is `validated`), so the D25 parity test
ignores exactly the JITs' "unsupported: GC types" lines until they claim `gc` (steps 3b-4), as it
did for exceptions in S0012 (see Changes, step 2). The oracle is
wasmtime-py 50.0.1 with the `is_i31` workaround (LESSONS 100, wasmtime#15216: drop it when a
release built with the fixed Rust toolchain is pinned). Work happens on the branch `gc` (PR 7).

**Before step 1a** the reader raised `NotImplementedError` for the type forms 0x4E-0x50, 0x5E, 0x5F
("rec / sub / struct / array types"), the value types 0x6A-0x6E and 0x71-0x73, and the prefix
0xFB (step 1a, 2026-11-11: the types are read, validated and linked; `frontend.types.key` replaced
`validate.functype_key`, see Changes). Type identity was `validate.functype_key`, a structural key per function type, used by
`link.py`, `pyc` (`f.s` strings, now keys) and the JIT's process-wide `_TYPE_IDS`. The JIT pins only
`i32`/`i64` locals (`compiler.choose_pins`), so a reference never lives in a pool register.

**The design in one paragraph** (revised 2026-11-06 for the maintainer's decision: a copying
collector with precise roots from stack maps). The front end gains the GC type system once: rec
groups, iso-recursive canonical keys and subtyping, used by every target and by linking. On `pyc` a
struct is a Python list `[rtt, fields…]`, an array `[rtt, data]`, an i31 a Python int, and Python's
own collector reclaims everything, cycles included. On the JITs every store has one **GC heap**,
kept as a hidden i32 linear memory of each instance (4 GiB + guard reserved, never moves). A GC
reference is a 32-bit offset into it, an i31 is `(v << 1) | 1`. Struct and array accesses are
loads and stores on that memory, so they reuse S0011's bounds and guard pages. Allocation bumps a
cursor in code; only a full semispace calls a host service. The GC lowering is written once, in the
shared JIT core, over existing D39 methods. The collector is a **Cheney semispace copier**: two
halves of the heap, live objects copied from one to the other, every reference to them rewritten in
place. That needs **precise roots**: the shared core writes a **stack map** per call site (which
value-stack slots hold references), each backend records where its native frame keeps the return
address, the host bridge records the stack pointer of every exit from wasm, and the runtime walks
the frames of the store by their return addresses. Calls between wasm functions gain no
instruction. A map marks a reference slot only where a **liveness analysis** in the core finds it
still live; the walk nulls the dead ones. Every other root (globals, tables, element segments, host
handles) is precise and updated in place. **Exception objects move into the GC heap** (as in
Wasmtime): an `exnref` becomes a u32 offset, a `throw` allocates like `struct.new`, and D52's arena
is removed (step 6).

## Goals / Non-goals
* Goals:
  * `gc/` passes on `pyc`, `jit-x86_64` (guard and explicit) and `jit-aarch64` at parity, and the
    78 expected failures of each target are gone.
  * Unreachable objects are reclaimed on every target, cycles included. Wasmtime's default
    collector leaks cycles (measured below); ours does not. Exception objects are reclaimed too
    (step 6), which closes D52's deviation.
  * Every root the JIT collector updates is found by type, never by guess; the frame walk is
    checked against the runtime's own record of each entry.
  * The machine code of every module is byte-identical on both JITs except where the module uses
    GC types or instructions (D35 lists), CoreMark included. Stack maps are data next to the
    code; the trampolines (process-wide, not module code) change.
  * The JIT's GC semantics and its stack maps are written once for both architectures (D53).
  * The contract changes are stated once: the type keys, the context words, the trampolines, the
    stack-map section, the trap codes, the object layout and the runner's result forms.
* Non-goals:
  * The public API for GC values (`AnyRef`, `StructRef`, rooting scopes, `Store.gc()`): phase 6.
    Until then a handle given to the host stays alive until its store is dropped (Q10).
  * Generational or incremental collection, write barriers, a large-object space, compressed
    references (Q2).
  * Reclaiming host values passed in as `externref` (kept until the store is dropped, as today).
  * Shared GC objects (shared-everything threads): not planned (WASM-PROPOSALS.md).
  * Custom descriptors and the JS string builtins.
  * `mpy`: phase 7. The `pyc` mapping is chosen so that it carries over (Q6).
  * Stack switching.

## Interface

### Types in the front end (shared by every target)
* **Reader.** Type section entries: `rec` (0x4E) groups, `sub` (0x50) and `sub final` (0x4F) with
  at most one supertype, composite types `func` (0x60), `struct` (0x5F), `array` (0x5E). Field
  storage types add `i8` (0x78) and `i16` (0x77), each with a mutability byte. Abstract heap
  types: `any` 0x6E, `eq` 0x6D, `i31` 0x6C, `struct` 0x6B, `array` 0x6A, `none` 0x71, `noextern`
  0x72, `nofunc` 0x73, beside today's `func`, `extern`, `exn`, `noexn`. A function type keeps
  today's `(params, results)` shape. Composite types, supertypes, `final` and rec-group bounds go
  into new lists of the module dict, so existing readers of `mod["types"]` do not change.
* **Instructions** (0xFB 0-30): `struct.new`, `struct.new_default`, `struct.get`,
  `struct.get_s`, `struct.get_u`, `struct.set`, `array.new`, `array.new_default`,
  `array.new_fixed`, `array.new_data`, `array.new_elem`, `array.get`, `array.get_s`,
  `array.get_u`, `array.set`, `array.len`, `array.fill`, `array.copy`, `array.init_data`,
  `array.init_elem`, `ref.test`, `ref.test null`, `ref.cast`, `ref.cast null`, `br_on_cast`,
  `br_on_cast_fail` (cast flags byte, label, two heap types), `any.convert_extern`,
  `extern.convert_any`, `ref.i31`, `i31.get_s`, `i31.get_u`. Plus `ref.eq` (0xD3), already
  decoded as a simple opcode.
* **Constant expressions** add `struct.new`, `struct.new_default`, `array.new`,
  `array.new_default`, `array.new_fixed`, `ref.i31`, `any.convert_extern` and
  `extern.convert_any`. Global initializers, table initializers and element items can allocate.
* **Canonical keys (iso-recursive).** One function, `frontend.types.key(mod, i)`, replaces
  `functype_key` for every user. The key of type *i* is the SHA-256 hex digest of
  `(group, k)` (deterministic: the same in every process and on every machine, no shared state): the rec group's composite types, supertypes and `final` flags,
  with a reference inside the group written as `("rec", j)` and a reference outside it written as
  that type's (already computed) key, and *k* the position in the group. Keys are computed group by
  group in index order, so a key is never a nested tree. Two types are equivalent across modules if and only if their keys are equal (the spec's
  "type equivalence"). For every type valid before step 1a (singleton groups; a self-reference is
  `("rec", 0)`) the key is equivalent to the old `functype_key`, so no current result changes;
  `pyc` compares the key of a function's type (its `f.s`), not its parameter and result shape, so
  rec groups and finality count there as in the JIT.
* **Subtyping.** Declared supertypes, checked as the spec says: the supertype is not final, a
  struct subtype extends the supertype's fields (immutable fields covariant, mutable invariant),
  an array likewise, a function contravariant in parameters and covariant in results. The
  abstract order: `none ⊑ i31, struct, array ⊑ eq ⊑ any`; every concrete struct ⊑ `struct`,
  array ⊑ `array`, function ⊑ `func`; `nofunc`, `noextern`, `noexn` are the bottoms of the three
  other hierarchies. A type index may refer only to earlier rec groups or its own.
* **Linking.** `link.py` matches imports with subtyping: a function import if the exported
  function's type is a subtype of the declared one, an immutable global covariantly, a mutable
  global and a table element type by equivalence, a tag by equivalence (S0012). This closes
  `linking.wast:112`.
* **Reference masks at call sites** (for the JIT's stack maps, Q3). The validator already keeps
  the operand types. For a module that has an any- or extern-hierarchy value type anywhere, it
  records for each call instruction (`call`, `call_indirect`, `call_ref`, every instruction the
  JIT lowers to a service call, every allocating GC instruction) which operand-stack positions
  below the instruction hold such a reference. Language-neutral data, used only by the JIT.

### Values per target
| value | `pyc` | JITs (64-bit slot) |
|---|---|---|
| null of any hierarchy | `None` | 0 |
| `i31` | Python int, the signed value (fits MicroPython's 31-bit small ints, LESSONS 18) | `(v << 1) \| 1`, zero-extended |
| struct of type *t* | `[rtt_t, f0, f1, …]` (a Python list) | offset of the object in the store's GC heap, a multiple of 8; changes when the collector moves the object |
| array of type *t* | `[rtt_t, data]`: `data` a `bytearray` for `i8`, a list otherwise | as a struct |
| a host value as `externref` | the object itself | `(h << 2) \| 2`, *h* the store's handle number (today `h`) |
| a host value as `anyref` (`any.convert_extern`) | `_Host(v)`, a private box | the same word: the conversion is a no-op |
| a GC value as `externref` (`extern.convert_any`) | `_Ext(x)`, a private box (unboxed by `any.convert_extern`) | the same word |
| `funcref` | unchanged | unchanged: a function record's address, never moved |
| `exnref` | unchanged (S0012) | until step 6 an arena address (D52); from step 6 the u32 offset of an exception object in the GC heap, moved like any object |

* An RTT is the canonical runtime type: on `pyc` an `_RTT` object per canonical key in a
  process-wide registry (`kind`, `final`, `depth`, `display` = the tuple of supertypes by depth,
  ending with itself); on the JIT a type-info record in the GC heap (below).
* Field values are stored as the target stores locals: `pyc` floats as Python floats (or bits,
  D46), packed fields masked to their width; JIT fields in their natural size.
* On the JIT the low two bits classify an any-hierarchy word: `x1` i31, `10` host value, `00`
  an object (or null). The `externref` re-encoding is runtime-only: no JIT instruction reads an
  externref's bits except the null test, so no code changes (identity).
* Because `extern.convert_any` is an identity, **any `externref` slot may hold a GC object**,
  also in a module that declares no GC type. Stack maps therefore cover externref slots of every
  module, and the collector decides by the low bits of each word.

### JIT: the GC heap
* **One heap per store**, created with the first instance whose module uses GC types or, from
  step 6, an exception instruction (`throw`, `throw_ref`, `try_table`): the reservation and the
  header page then, the semispaces committed at the first allocation (Q7). It is a runtime
  `Memory` (an i32 memory: 4 GiB + 32 MiB reserved, committed on growth, never moves; S0006,
  D50 point 4). It is bound into every GC-using instance as a **hidden memory** whose index is
  the module's number of declared memories, so its `base` and `size_bytes` words follow the
  module's own memory words. `memory.size`, `memory.grow` and the libcall immediates do not see
  it (they count declared memories), so their code does not change.
* **Regions of the reservation** (offsets):
  * 0-63, the header area, holds no object: offset 0 is null, the allocation cursor is the u32 at
    8 and the limit the u32 at 12. Code reads and writes them as ordinary heap words.
  * 64 KiB to 64 MiB, the **type-info area**: permanent, never collected, never moved, committed
    as types are registered. A store that registers more type information than this fails
    instantiation with "GC type area exhausted" (about 10⁶ struct types of four fields).
  * 64 MiB to 4 GiB: **two semispaces** of equal reserved size, `A` = [64 MiB, 2 GiB + 32 MiB)
    and `B` = [2 GiB + 32 MiB, 4 GiB). Objects live in the active one; each is committed from its
    start to the current semispace size *S* (Q2).
* **Object layout** (after Wasmtime's `VMGcHeader` and array length; its GC RFC and
  `crates/wasmtime/src/runtime/vm/gc`): every object starts at a multiple of 8 with a u32
  type-info offset and a u32 of collector bits (bit 0: forwarded; zero while wasm runs). A
  struct's fields follow at their natural alignment in declaration order (an exception object,
  step 6, is a struct whose first field is the u64 tag identity at 8, then the tag's parameters): `i8` 1, `i16` 2,
  `i32`/`f32` 4, `i64`/`f64` 8, `v128` 16 (unaligned access, as D41), an any- or
  extern-hierarchy reference 4, an `exnref` 4 (8 until step 6), a `funcref` 8. An array has its u32 length at 8 and
  its elements from 16. The smallest object is 8 bytes, which is room for the forwarding offset:
  a copied object's old header becomes `{new offset, bits = 1}`.
* **Type-info records** live in the type-info area, written once per canonical type the store
  uses: kind (struct, array, func), `final`, the byte size (struct) or element size (array), the
  subtype depth *d*, the display (*d* + 1 record offsets, the last its own), and the offsets of
  the reference fields the collector traces (an array: whether its elements are references). A
  type's identity in a store is its record offset, so a cast to a final type is one compare with
  the RTT context word. Records never move, so RTT words never change.
* **Allocation** (inline, in code): spill, load cursor and limit, `new = cursor + size`; if
  `new > limit`, call the allocation service (cold code at the function's end); store the cursor;
  write the header; then **write every field** from its operand slot, or its default for the
  `_default` forms (one store per struct field; `memory_fill` on the heap for an array). The
  collector never zeroes memory, so a semispace can be poisoned freely (Q2). An allocating
  instruction is a call for the lazy stack: the operand stack is in slots before it.
* **Services** (host functions with the libcall signature, called through the bridge): the
  allocation slow path (a collection or growth, then the object), the subtype test of a function
  type that is not final (Q11), and the bulk array operators that are not a plain
  `memory.copy`/`memory.fill` on the heap: `array.new` and `array.fill` of elements wider than a
  byte, `array.new_data`, `array.new_elem`, `array.init_data`, `array.init_elem`. Operands and
  immediates are passed in slots, as for the libcalls. **A service that may allocate reads its
  reference operands from the slots after any collection it runs, never before**, and never keeps
  a raw reference in a Python variable across a collection. An inline loop replaces a service
  only with a measurement that it pays.

### JIT: lowering (written once, Q9)
GC instructions are lowered in the shared core (a new `jit/common/gc.py` called by
`common/compiler.py`, as `common/simd.py` is) onto existing D39 methods. No `ll_*` op is added;
S0011's `bounds` and fault points apply to every heap access unchanged.
* field and element accesses: `load` and `store` (the `_s`/`_u` widths for packed fields, `simd`
  for v128) with the hidden memory's index;
* null checks: `null_check(f, x, NULL_REFERENCE)`, omitted when the static type is non-nullable;
* array bounds: `cmp_branch(ge_u, i, len, L)` to a `trap(ARRAY_OUT_OF_BOUNDS)` stub; the element
  address `ref + 16 + i·size` is formed in 32 bits with `binop`, so even a corrupt length cannot
  leave the 4 GiB reservation;
* `array.copy`, and `array.fill` and `array.new` of `i8` elements: `memory_copy` and `memory_fill`
  on the heap, after the array bounds checks (memmove semantics, no barrier needed);
* i31: `binop` (`shl`, `or`, `shr_s`, `shr_u`); `ref.eq`: `cmp_set`/`cmp_branch` on 32 bits;
* casts: `binop and` and compares on the tag bits, `load` of the header and of the display entry,
  compares with the RTT context word (`ctx_load`); `br_on_cast*` are `cmp_branch`es to labels;
* allocation: `load`/`store` of the cursor and limit, `binop add`, `cmp_branch`, `call_host` to the
  service, then the field stores;
* a cast of a `funcref` to a concrete function type: the record's type-id word against the RTT,
  through a service (Q11).

The 0xFB opcodes enter each backend's `supported` set, which D39 allows without an amendment.

### JIT: safepoints and stack maps (Q3)
A **safepoint** is every call site: `call_direct`, `call_record`, `call_indirect`, `call_ref`,
`call_host` (libcalls and services) and the call inside each host thunk. Any call may reach an
allocation (through another function, a host function and a nested entry), so every call site of
every module is one. A tail call is not a safepoint (its frame is gone); the inline allocation
fast path is not one (it calls nothing). Collections happen only inside the allocation service.

**The invariants the maps rely on.** Each is stated in the core next to the code that keeps it,
checked by an assertion where it can be, and has a test and a mutation (Test plan):
* **I1** an any- or extern-hierarchy reference is never in a pool register: `choose_pins` pins
  only `i32`/`i64` locals (an assertion in the core, a test with heavily used `anyref` locals);
* **I2** at every call the operand stack is in slots (D39; `flush` before every call), and only
  pins are live across a call: `tos` and the scratch registers are dead;
* **I3** a slot a map marks as live holds a valid reference word on every path to the site:
  reference locals are zeroed by the prologue (wasm's default is null), operands are written by
  `flush`, and a reference slot dead at an earlier safepoint was nulled by that walk;
* **I4** after a safepoint a reference is read again from its slot: no reference, and no address
  formed from one (`ref + offset`), is kept in a register across a call (follows from I2).

**Map content.** Per function, the bitmap of its reference-typed local slots (parameters
included); per site, a bitmap over the frame's value-stack slots `[0, h)` in the core's slot
numbering (v128 = two slots, D41) of the reference slots **live** at the site:
* a reference local is live at a site if some path from the site reads it before writing it
  (Q3); until the liveness step (step 7) every reference local is marked at every site;
* an operand slot below the call's arguments whose type is a reference (the validator's mask) is
  live unless its value's only consumer is `drop`; for a wasm call, `h` stops at the arguments,
  which belong to the callee's frame and are in its map as parameters; for a service call, `h`
  includes the service's argument slots, so a reference operand of `array.new`, a field of
  `struct.new` or a payload value of `throw` is updated if the service collects.
`funcref` and v128 slots are never marked (records do not move); `exnref` slots are marked from
step 6. The walk **nulls every reference slot of the function that the site does not mark live**,
so a dead slot never keeps a stale offset into the old space: marking a dead slot by mistake is
then only retention, while dropping a live one is a wrong result the stress and poison modes show
(Q3).

**Who writes what.**
* The shared core (the stack-map part of `jit/common/gc.py`, the liveness pass in
  `jit/common/liveness.py`) builds each site's bitmap from the function's local types, the
  validator's mask and the live sets, and the slot shift: the distance from this
  frame's base to the callee's base (`shift_slots` of a wasm call; 0 for a service call, which
  never calls a wasm frame, and in a host thunk). These are the same for both architectures.
* Each backend records, in every call method and in `host_thunk`, the code offset just after the
  call and two native numbers: `ret_at`, the bytes from the stack pointer at the call (before
  x86-64's `call` pushes) to the slot that holds this frame's own return address, and `up`, the
  bytes from that stack pointer to the caller's stack pointer at its own call (x86-64: pushed pins, pad, and the 16 bytes a record call pushes;
  aarch64: the frame record and pins, and the 16 bytes a record call pushes). This is a D39
  amendment (Q9): the call methods gain an output, no operand changes, and their code is
  byte-identical.
* The trampolines (entry, bridge, `tail_switch`) carry a small table of their own: the entry's
  return point ends a segment, `tail_switch`'s `restore` point steps over the restore frame (the
  saved context, then the real return address).

**The exit record** (an amendment of the context ABI, Q5). Each store has three words `{sp, pc,
frame}`, and **context word 14 `EXIT_RECORD`** holds their address in every context of the
store, GC or not (as words 12 and 13 hold the arena's addresses until step 6). The bridge writes them first,
at every host call: the calling frame's stack pointer at the call (before x86-64's `call`
pushed), the return address into the calling code, and the frame register (r12, aarch64
`FRAME`, which a service call does not move); and writes `sp = 0` before it returns. Each entry
trampoline saves the three words on the native stack and restores them when its call returns,
and also saves the frame it was given. These are the native-stack anchors Wasmtime keeps as
`last_wasm_exit_fp/pc` and `last_wasm_entry_fp` (older activations saved by its runtime), and
HotSpot as the "last Java frame"; here the saving is done in machine code by the entry
trampoline. Cost: no instruction on a call between wasm functions; about five more instructions
per host call and about eight per entry, on paths that cost at least 0.3 µs each (ctypes,
LESSONS 9); measured at step 3a.

**The walk** (runtime, Python, inside a collection). Start at the store's exit record: the
innermost frame is suspended at the call whose return address is `pc`, with stack pointer `sp`
and base `frame`. For each frame: find the code blob of the return
address (a sorted list of the store's code ranges), its site (a dict per blob); update the marked
slots; step: the caller's return address is at `sp + ret_at`, the caller's stack pointer at
`sp + up`, the caller's base at `base − 8·shift` of the caller's site. A return address equal to
an entry trampoline's return point ends the segment: the trampoline frame holds the saved exit
record of the enclosing host call (the next segment) and the entry's frame, which must equal the
base the walk computed; a saved `sp` of 0 ends the walk. Frames of other instances of the store
and host thunks are walked the same way; tail calls need no special case, because each frame is
identified by its own return address. An unknown return address or a base mismatch is an internal
error that aborts the collection with a `RuntimeError`, never a guess. Measured: 0.5 µs per frame
in Python plus 0.1-0.2 µs per marked slot (Measurements).

**Check mode** (`WABOROS_JIT_WALK_CHECK=1`, tests only): every host call and libcall walks the
whole stack of the store and checks the segment count against the runtime's active entries and
every segment's base against its entry. It runs on code without GC, so the frame layouts are
verified on the whole spec suite before any object moves (step 3a).

### Roots and the collector (JIT; Q2, Q4)
Collections happen only in the allocation service. Allocations made by the runtime itself
(instantiation, constant expressions) grow the heap and never collect. Every root is precise:
* **Frames**: the walk above, across nested entries and every instance of the store.
* **Globals**: the reference-typed global words of every instance of the store (an imported
  global through its owner's word only).
* **Tables**: every element word of each any- or extern-hierarchy table of the store.
* **Element segments**: the passive segments not yet dropped (runtime lists).
* **Host handles**: the store's handle table; the host holds handle numbers, never raw references
  (Q10).
* **Exception objects**: in step 5 the arena objects (D52) are still outside the heap, but a
  payload may hold GC references (a tag with an `anyref` parameter), so the step-5 collector
  scans every arena object by its tag and rewrites those fields (about 40 lines, removed with the
  arena in step 6); from step 6 they are heap objects, traced like structs through their tag type's
  record, reached from slots, globals, tables and other objects. The store's pending-exception
  word (word 10's target) is a root too: an exception is in flight only between a `throw` and
  its landing pad or entry, where no allocation happens, so this is a defence, checked by the
  verify switch, not a path a test can reach (Q7).
* **The runtime**: nothing else. A service reads its reference operands after collecting; entry
  arguments are written to the frame just before the call and results converted to handles
  just after it, with no allocation between.

**Collection** (Cheney): flip the semispaces; copy each root's object into the new active space
(the bump cursor) unless its header is already forwarded, leave `{new offset, 1}` in the old
header, rewrite the root; then scan the new space from its start to the cursor, object by object
(its size from its type-info record and, for an array, its length), forwarding every reference
field the record names. Words with low bits other than `00`, and null, are left alone. An object
of any size is copied whole (`memmove`). Afterwards the cursor and limit words point into the new
space; the old space is left as it is (or poisoned).

**Policy**: collect when the active semispace is full. After a collection with *L* live bytes and
a request of *r* bytes: if `2·(L + r) > S`, grow *S* to `min(S_max, max(2·S, 2·(L + r)))` by
committing both halves (the reservation never moves, so no copy and no resize dance: Wasmtime
grows its heap memory at the end and resizes its halves only when the first half is active).
*S* starts at 1 MiB per semispace. `S_max` = 2 GiB − 32 MiB. If `L + r > S_max` the allocation
fails as Wasmtime's does (Semantics). The old space is never decommitted (RSS up to 2·*S*; a
per-OS `madvise` release only with a measurement, D47).

**Test switches**: `WABOROS_JIT_GC_STRESS=1` sets the limit to the cursor, so every allocation
takes the slow path and collects (every object moves at every allocation);
`WABOROS_JIT_GC_POISON=1` fills the old space after each collection, and the free part of the
active space, with a pattern; `WABOROS_JIT_GC_VERIFY=1` checks after each collection that every
root and every reference field of the new space points at an object start inside it.

Written in WAT from step 5 (Q4): `src/waboros/runtime/gc/collector.wat` is the source and the
committed `collector.wasm` beside it is package data; a test assembles the `.wat` (`tests/watcache.py`,
`wasm-tools` is a development tool only) and fails unless the bytes equal the committed file. No tool
runs at install or import: the JIT compiles the module the first time a store needs it. The module
is core wasm only (no GC types, exceptions or tail calls), imports the hidden memory, has no host
import, is deterministic (D35), and traps (`unreachable`) on a malformed heap instead of writing
outside it. If the WAT grows too large or too intricate, the collector is written in C instead,
under D54's C rule (pinned `ziglang` or wasi-sdk, committed `.wasm` with a byte-match test, an
allowed-instruction test, a native sanitizer build of the same file); the choice is made in step
5's plan, which also fixes where the C module's data and stack sit in the hidden memory (outside
every object: the header area and the type-info area are the candidates). If C is chosen, the plan
also fixes (maintainer, 2026-11-10):
  1. *Offsets, not pointers.* `collector.c` reaches the heap only through a base plus a u32 offset
     (a macro such as `H(off)`), never through `T*`: GC references are u32 offsets anyway, the
     base is 0 in the wasm build (the imported hidden memory) and a test-allocated buffer in the
     native build, so the sanitizer build checks the same code the JIT runs.
  2. *The module's structure, not only its instructions.* clang places data freely: active data
     segments at linker addresses, `__stack_pointer` as a global, possibly `memory.grow`. The test
     also checks the imports (the memory only), the exports, that every data segment and the stack
     lie in the reserved region (`--global-base`, `-z stack-size`), and that there is no
     `memory.grow`; otherwise the instruction test passes while the module writes its statics over
     the heap.
  3. *Where the byte-match test runs.* That the same `ziglang` wheel gives the same bytes on Linux,
     macOS and Windows is not verified: the plan either proves it once on all three (then the gate
     may run anywhere) or runs the gate on a Linux job only, so a host difference is not a false
     failure.
The module also carries the subtype check of non-final types (Q11: JIT code calls it directly, as a
call between instances, without Python; the site stays a safepoint) and the allocation primitive
used for allocating constant expressions (one allocator; their evaluation stays in Python). Its
exports, fixed in step 5's plan, are `collect`, `is_subtype` and `alloc` (RUNTIME-MODULES.md).
Python keeps the frame walk, which gathers every root (frames, globals, tables, element
segments, handles, the step-5 arena fields) into a roots buffer the module rewrites, the growth
policy and the verifier. A collection is atomic: the module does not poll the interrupt word (a
trap halfway through a copy would leave the heap half moved); the entry releases the GIL like any
JIT entry, and an interrupt is seen at the next poll after the service returns. With
`WABOROS_JIT_GC_VERIFY=1` Python checks, independently of the module, the heap's form (every root
and reference field points at an object start of the new space, headers and type-info records
consistent) and its content: a canonical digest of the graph reachable from the roots (types,
shapes and non-reference fields, references numbered in walk order, not by offset), taken before
and after the collection, must be equal. `pyc` has no collector (Q6: Python lists).

### Context ABI (an amendment of v1, Q5)
* **Word 14 `EXIT_RECORD`** (was reserved): the address of the store's exit record, in every
  context. Word 15 stays reserved.
* **The bridge** writes the exit record at every host call and clears its `sp` before returning;
  **the entry** saves and restores it and saves its frame (above). New rows of ARTIFACT.md's
  per-architecture table say where each architecture finds `sp`, `pc` and `frame`.
* The hidden memory's two words, after the module's memory words (GC modules only).
* A **GC group** appended after the tag words, so no existing offset moves: the allocation
  service, the other services (above), and one RTT word per type the module allocates, casts to or
  tests (the type-info record's offset in this store).
* No word but 14 changes in a module without GC types, and its code does not change.
* From step 6 (exceptions in the heap): words 11-13 (`EXN_REFILL`, `ARENA_CURSOR`,
  `ARENA_LIMIT`) become reserved, zero; word 10 still points to the pending-exception word, which
  holds a u32 offset; a module with an exception instruction gets the hidden memory's words and
  the GC group (the allocation service, an RTT word per tag type it throws), so its code and
  context change.
* `externref` words become `(h << 2) | 2` (runtime-only, above).

### Artifact (format v1, Q5)
* `TYPES` carries the rec groups and composite types; the context-group sizes follow from them.
* **A new section `STACKMAPS` (id 15), in every JIT artifact.** Sketch, little-endian:
  `u32 nsites`; per site, sorted by code offset: `u32 ret` (the code offset just after the call),
  `u32 shift`, `u16 ret_at`, `u16 up`, `u32 map` (an index into the bitmap pool, 0 = no
  reference); then the pool: per map `u32 nslots` and `ceil(nslots / 32)` u32 words. 16 bytes
  per site plus the pool. Measured on today's modules (no reference types in most): CoreMark 108
  sites, 1.7 KB (5.1 % of its 34 KB of code); the corpus (`mono`, `hash`, `zip`) 384 sites,
  6.1 KB (3.5 %); the spec suite 2 022 sites in 2 385 modules, 32 KB (2.7 % of 1.18 MB).
* A loader refuses an artifact without the section (every frame of a store must be walkable).

### Trap codes
| code | name (Wasmtime's) | raised by |
|---|---|---|
| 10 | `NULL_REFERENCE` (exists) | `struct.get/set`, `array.*`, `i31.get_*` on null (Wasmtime 50: also for i31) |
| 16 | `ARRAY_OUT_OF_BOUNDS` | element index or range past the length |
| 17 | `CAST_FAILURE` | `ref.cast` |
| 18 | `ALLOCATION_TOO_LARGE` | an array whose JIT object would exceed 4 GiB |

`array.new_data`/`array.init_data` past the segment trap `MEMORY_OUT_OF_BOUNDS`, the `_elem`
forms `TABLE_OUT_OF_BOUNDS`, as the spec texts say. `base.TrapCode` and the runner's `TrapCode`
gain the three codes. The JIT's host-call status set is derived (`frozenset(TrapCode) - {UNCAUGHT_EXCEPTION}`, the one
exception named next to it, LESSONS 91), so code 16-18 from a host function is a host trap, as any
wasm trap code is, not a new meaning.

### `pyc`
* `runtime._RTT`, `_Host`, `_Ext`, and helpers `_tcast`, `_taob`, `_ttoolarge`, `_refeq`.
* `struct.get`: `x[k + 1]`, preceded by `if x is None: _tnull()` only for a nullable static type.
  Packed `get_s` sign-extends. Arrays: `d = x[1]`, an explicit `i < len(d)` check, never a `try`
  around a trapping operand (LESSONS 95).
* Casts: `x.__class__ is int` (i31), `x.__class__ is list` and `x[0].kind` (struct/array),
  `x[0] is T` for a final T, else `x[0].depth >= d and x[0].display[d] is T`.
* `ref.eq`: `is` when neither static type can be i31, `==` when both are `i31ref`, else `_refeq`
  (`a is b or a.__class__ is int and a == b`). `==` is never used on lists.
* `call_indirect`: `f.s` stays the function type's key (code of a module without GC is
  unchanged); a final expected type is the key comparison (all of today's modules), a non-final
  one `q != key and not _fsub(q, RT<i>)`: the registry lookup of `q` and the display test.
* `array.new` with a length whose JIT object would exceed 4 GiB traps `ALLOCATION_TOO_LARGE`, so
  both targets trap at the same lengths. Step 2 finds Wasmtime's exact bound per element size by
  bisection through wasmtime-py and uses it on every target.

### Runner and oracle (S0001)
* `TrapCode` gains the three codes; texts: `cast failure`, `out of bounds array access`,
  `null structure reference`, `null array reference`, `null i31 reference` (the last three
  `NULL_REFERENCE`).
* Values: `HostRef(n)` (written `(ref.host n)`), and a result kind for a non-null reference
  (`i31`, `struct`, `array`, `host n`, `func`, `extern`) so the runner can check `i31ref`,
  `structref`, `arrayref`, `eqref`, `anyref N` and a valueless `externref`.
* Wasmtime adapter: classify with the C library's `wasmtime_anyref_i31_get_u/_is_struct/_is_array`;
  take parameter and result types from our own parse of the module instead of `func.type()`,
  which aborts on a concrete reference type (Q12).

### Rows (D47)
None. Nothing in this spec differs by operating system. Releasing the old semispace's pages
(`madvise`) would be per-OS code and is not part of it.

## Semantics
* **Casts** follow the spec. `ref.test`/`ref.cast` to an abstract type test the tag bits and the
  record's kind; to a concrete type compare the record offset (final) or the display at the
  target's depth. `null` variants accept null. `br_on_cast_fail` branches on failure. A host
  value internalized with `any.convert_extern` is `any` and nothing below it.
* **Conversions** are identities on the JIT and round-trip on `pyc`: `extern.convert_any`
  of `any.convert_extern(x)` is `x`, and the reverse, null to null (`gc/extern.wast`).
* **i31:** `ref.i31` keeps the low 31 bits; `i31.get_s` sign-extends them, `i31.get_u`
  zero-extends; two i31 values are `ref.eq` when their values are equal.
* **Trap order** is Wasmtime's, the first trap in program order: the operands are evaluated,
  then null, then bounds, then the access (LESSONS 95).
* **Allocation limits.** Measured with wasmtime-py 50.0.1 (2026-11-05): `array.new_default` of
  2²⁹ − 2 `i64` elements (about 4 GiB) and of 2³² − 1 `i8` elements trap
  `ALLOCATION_TOO_LARGE`; 2³¹ `i8` elements are allocated. A heap that cannot grow (3 000 live
  1 MiB arrays fit, 4 100 do not) is not a trap: "GC heap out of memory", a `WasmtimeError`.
  Ours: the JIT's service returns status 13 with a `MemoryError("GC heap out of memory")` pending
  (as a host error, D34); `pyc` lets Python's `MemoryError` propagate the same way. The JIT's
  live data is limited to one semispace, 2 GiB − 32 MiB (about 2 000 live 1 MiB arrays), where
  Wasmtime's default collector holds about 4 GiB: a deviation, recorded in DECISIONS.md at step 5.
  Wasmtime's own copying collector halves its heap the same way. An array between 2 GiB and
  4 GiB is not `ALLOCATION_TOO_LARGE` on the JIT but "GC heap out of memory", as on a full
  Wasmtime heap.
* **Collection is invisible to wasm.** Objects move, but no wasm instruction can observe an
  offset: `ref.eq` compares two words the collector rewrote together, i31 and host words never
  change, and the host sees handles.
* **Interrupts and threads.** A collection runs inside a host call: on the JIT the collector module
  runs in a JIT entry (the GIL released, as for any entry), and the one-thread-per-store rule (ARCHITECTURE.md, "Long calls and the
  GIL") keeps other threads out of the store. An interrupt is seen at the next poll after the
  service returns; a collection is never cut in half.
* **The host boundary.** A reference returned to the host is an opaque handle of its store, kept
  in the handle table (a root, updated when its object moves) until the store is dropped (Q10). A
  host value passed for an `anyref` parameter is internalized as `any.convert_extern` would. A
  handle of another store, or an object the runtime did not hand out, is a `TypeError` (LESSONS
  35).
* **Exceptions.** From step 6 an exception is a GC object: a `throw` allocates it (and may
  collect first, so a `throw` is a safepoint with its payload in the map), the landing pad reads
  the tag identity and the payload through the pending word's u32 offset, and an unreachable
  exception is reclaimed. Status 14 propagation (D52) is unchanged. At an entry the runtime turns
  an uncaught exception's payload into host values and handles before any other wasm runs. `pyc`
  is unaffected (Python objects).

## Measurements
Dev VM: Intel Xeon @ 2.10 GHz, 4 cores, CPython 3.13.17, wasmtime-py 50.0.1, `jit-x86_64` in
`auto` (guard) mode. Scratch modules and scripts written for this spec, not in the tree; medians
of alternated runs.

First draft (2026-11-05):
* **wasmtime-py 50's default collector (DRC; Wasmtime's `main` has since made the copying collector the default, `Collector::Auto`)**, a loop of `struct.new` + `struct.get` whose objects die
  at once: 79, 61 and 47.5 ns per iteration at 10⁶, 10⁷ and 5·10⁷ iterations, maximum RSS
  flat at 26 MiB. Building and walking a live list of 10⁶ nodes: 105 ns per node.
* **Wasmtime leaks cycles:** 10⁷ dropped two-object cycles end at 697 MiB maximum RSS, 3·10⁷ at
  2 528 MiB (348 ns per cycle as it pages). A copying collector and `pyc` reclaim them.
* **The lowered shape** (Q1): the same two loops hand-written in WAT the way this spec lowers them
  (heap as memory 1, bump cursor, slow path a call): churn 6.6 ns on `jit-x86_64` (Wasmtime on
  the same WAT 4.8 ns, Wasmtime's real GC 44.7 ns); list 9.6 ns (8.7, 78.2). Not the
  implementation, its instruction shape.
* **Heap base from the context** (Q1): a pointer chase on memory 1 (base read from the context at
  each access) against memory 0 (base in `r13`): 2.36 against 1.83 ns per step of two loads in a
  1 000-node cycle that fits L1, 64.6 against 63.0 ns over 10⁶ scattered nodes.
* **Start map** (the rejected conservative scan): one shift and one byte store per allocation:
  churn 7.50 → 8.55 ns, list 11.49 → 11.86 ns. The copying design has no start map.
* **Marking** (the rejected mark-sweep), a binary tree of 10⁶ objects: Python over ctypes words
  462 ns per object, over a `memoryview` with the loop unrolled 312 ns; the same mark in wasm on
  `jit-x86_64` 5.7-6.3 ns (Wasmtime 4.4-4.8 ns, `pyc` 605 ns). A Python sweep object by object
  217 ns per object; the line-map sweep of a 256 MiB heap 8.4 ms; marking one object's lines
  121 ns.
* **`pyc` representation** (Q6), CPython 3.13: allocating a two-field struct as `[rtt, a, b]` 30
  ns, a `__slots__` class per type 93 ns, a list subclass 62 ns; reading a field 12, 10.8 and
  25 ns.

Revision (2026-11-06):
* **Copying against marking in Python** (Q2, Q4), one process, the same 10⁶-node binary tree of
  16-byte objects `{type, bits, left, right}` over a `memoryview` of u32 words, both semispaces
  touched before timing, 5 rounds alternated, two processes: Cheney copy median 700 and 708 ns
  per live object (range 623-948), mark of the same graph 352 and 390 ns (333-438). Copying is
  about 1.9× a mark per live object in Python; it has no sweep (the rejected design added 121 ns
  of line marking per object and a C-speed sweep). Copying small objects word by word instead of
  by slice gained nothing (705-1 060 ns).
* **The same Cheney copy written in wasm** (a 60-line scratch WAT, the collector of Q4 (b)): 10.9-
  13.8 ns per object on `jit-x86_64`, median 11.3 (Wasmtime on the same WAT 10.1-11.6, median
  10.8), to-space pages touched first: about 60× the Python copy.
* **Bulk bytes from Python** (ctypes, touched pages): `memset` 8.1-8.7 GB/s, `memmove` of 16 MiB
  4.9-6.0 GB/s; a `memset` of fresh pages 0.2 GB/s (page faults). Forwarding one element of a
  reference array in Python: 160-316 ns. So a large array costs its element scan, not its copy.
* **The frame walk** (Q3), a Python model of the walk over 10⁴ frames (return address read from a
  native-stack image, `bisect` over 50 code blobs, a dict per blob, the base stepped by the
  site's shift, the marked slots read): 514 ns per frame with no marked slot, 707 with 2, 1 902
  with 8.
* **Safepoints in today's modules**, counted by wrapping the x86-64 backend's call methods while
  compiling: the spec suite (2 385 modules compiled, 1.18 MB of code) 2 022 sites: 909
  `call_direct`, 352 `call_indirect`, 19 `call_ref`, 21 `call_record`, 366 `call_host`, 355 host
  thunks; CoreMark 108 (103 direct, 3 record, 2 thunks) in 34 023 bytes; the corpus 384 (383
  direct, 1 indirect) in 177 892 bytes. Sizes in "Artifact".
* **Wasmtime's copying collector** exists in Wasmtime 50 (cargo feature `gc-copying`; its
  `VMCopyingHeader` and `gc/copying.rs` are compiled into wasmtime-py 50.0.1's
  `_libwasmtime.so`), but the C API has no collector setter (no `wasmtime_config_*collector*`
  export), so the oracle runs DRC and the copier could not be timed through wasmtime-py.

## Alternatives considered
* **JIT references as 64-bit addresses** into store chunks, like D52's arena. One load per field
  access instead of two (measured above: 0.53 ns per two-load step in L1, 1.6 ns of 64 over a
  cache-missing walk). Against it: 8-byte reference fields; no containment (a collector bug
  reaches any address, R3); the bounds and guard code of S0011 would not apply; the collector
  could not be a wasm module over the heap. Rejected (Q1).
* **Non-moving mark-sweep with a conservative scan of the value stack** (the first draft): no maps,
  no ABI change, but a start map (+1.05 ns per allocation, a byte per 8 heap bytes, 3.56 GiB of
  objects instead of 4), retention while an integer equals an offset, fragmentation, and no way to
  move an object later. Rejected by the maintainer (2026-11-06).
* **Frame records on the value stack** (each call stores its site in the caller's frame, or each
  prologue its identity): a walk with no native-stack reading, but one or two stores per call,
  a slot more in every frame (every module's code changes) and a special case for tail calls.
  Rejected: the return addresses are already on the native stack.
* **A frame-pointer chain on x86-64** (as Cranelift's `preserve_frame_pointers`): takes `rbp`
  out of the pool and adds two instructions per frame. Rejected: the per-site `ret_at`/`up`
  numbers give the same walk for no instruction. aarch64 already keeps its frame record and may
  use it as a cross-check.
* **A shadow stack of references** (Binaryen's spilling pass, wasm2c style): stores on every call
  in every frame that holds a reference. Rejected: per-call cost, with the slots already there.
* **Deferred reference counting** (Wasmtime's default): increments and decrements on every
  reference store, barriers in code, precise stack scanning anyway, and cycles leak (measured).
  Rejected.
* **Mark-compact** (Lisp-2 or sliding): moves objects and keeps one heap, so the live limit stays
  near 4 GiB, but it needs a mark pass, then passes to compute addresses, update references and
  slide, and a mark stack; Cheney needs one pass and no stack. Not measured; rejected for now.
* **GC as backend methods** (a `gc` group in D39, as `simd`): the same semantics written twice,
  which D53 removed. Rejected while the D39 methods suffice.
* **`pyc` objects as `__slots__` classes per type:** 3× the allocation cost of a list (above).
  Rejected.

Sources read for the shapes: the Wasm 3.0 specification (type equivalence, matching, casts); the
Wasmtime GC RFC (`bytecodealliance/rfcs`, "wasmtime-gc") and its behaviour probed through
wasmtime-py 50 (the u32 raw `anyref` of its C API, trap codes, the 4 GiB heap, DRC's cycle leak);
Wasmtime's sources on its main branch, read 2026-11-06: the copying collector

## Open questions
* **Q1 JIT reference representation and heap.** (a) u32 offsets into a per-store heap kept as a
  hidden i32 memory (Wasmtime's shape); (b) 64-bit addresses into store chunks. (a) costs one more
  load per access (measured: about 0.25 ns per access in L1, 2.5 % on a cache-missing walk). It
  gives 4-byte reference fields, keeps a collector bug inside the reservation (R3), reuses S0011's
  bounds and guard pages with no new code, and lets the collector run over the heap as a wasm
  memory (Q4). With a copying collector it also makes the semispace flip a change of two u32
  words. Recommendation: **(a)**. A pinned heap-base register is an optimisation for later, with
  a measurement. Decision (maintainer, 2026-11-10): **(a)**.
* **Q2 The copying collector** (maintainer, 2026-11-06: copying with precise roots). Choices
  within it:
  * *Algorithm.* (a) Cheney semispaces: breadth-first, the new space is its own work queue, no
    mark stack, no recursion; (b) a depth-first copy with an explicit stack (better locality for
    lists and trees); (c) mark-compact (Alternatives). Recommendation: **(a)**, Wasmtime's
    choice too (its semi-space collector, Cheney worklist, bump allocation). (a) and (b) differ
    only in the order of the work list (queue or stack), so step 5 measures both: two builds of the
    collector module, and the comparison is the JIT mutator's time after collections (locality)
    as well as the collection pause. Microbenchmarks (a long linked list
    walked, a tree traversed, a reference array scanned, after several collections) and the GC
    program of the corpus (step 4b), whole run, the two orders alternated, medians, both bounds
    modes. (b) replaces (a) only if it gains on the microbenchmarks and on the corpus program
    beyond the spread between rounds (the code-placement rule); otherwise (a) stays and only its
    `.wasm` is committed. Decision (maintainer, 2026-11-10): measure both in step 5.
  * *Header and forwarding.* The 8-byte header `{type-info, bits}`: a copied object's old header
    becomes `{new offset, 1}`. No object is smaller than 8 bytes, so forwarding needs no extra
    word (Wasmtime needs 20 bytes because its forwarding reference sits after a 16-byte header).
  * *Large objects.* Copied whole with `memmove` (4.9-6.0 GB/s measured); the cost of a large
    reference array is its element scan (160-316 ns per element in Python), which a non-moving
    large-object space would not remove. Recommendation: no large-object space.
  * *Zeroing.* Allocation writes every field, defaults included, so the collector never zeroes
    (a `memset` of touched pages is 8 GB/s, about 2 ns per 16-byte object allocated, avoided) and
    poison can fill any free memory. Cost: one store per field of `struct.new_default`, a
    `memory_fill` for `array.new_default`. Recommendation: explicit initialization.
  * *Growth.* Semispace size *S* from 1 MiB, doubled (or set to `2·(L + r)`) when a collection
    leaves more than half of it live, by committing both halves; never shrunk. Copying costs at
    most one live byte per allocated byte. RSS up to 2·*S*.
  * *Live limit.* u32 offsets give a 4 GiB heap; two semispaces and the 64 MiB type area leave
    **2 GiB − 32 MiB of live data**. wasmtime-py 50's default (DRC) allows about 4 GiB (measured: 3 000
    live 1 MiB arrays fit, 4 100 do not); its copying collector also halves its heap. A deviation
    from the default oracle, recorded at step 5.
  * *Compressed references* (`u32 << 3`, 32 GiB): the scaled address is free in an x86-64
    addressing mode and in aarch64's `add …, uxtw #3`, but the heap is no longer an i32 memory
    (S0011's checks and the 4 GiB guard reservation no longer apply), and the tag bits of i31 and
    host words would have to move. That is a change of the reference word and of the ABI.
    Recommendation: **later**, only for a real program with more than 2 GiB live, as its own spec
    with a version bump.
  * Decision (maintainer, 2026-11-06): the 2 GiB − 32 MiB live limit is accepted as a deviation (recorded in
    DECISIONS.md at step 5); compressed references later, in their own spec.
  * Cost against the first draft: copying is about 1.9× a mark per live object in Python (700 vs
    352-390 ns, measured in one session), with no sweep, no start map (+1.05 ns per allocation
    removed), no fragmentation, and twice the committed memory. The cost of a collection follows
    the live data, not the heap.
* **Q3 Finding roots.** Precise, through stack maps (the conservative scan is out: a collector
  cannot rewrite a word it is not sure is a reference). Choices:
  * *What a map covers.* (a) every reference-typed local at every site, no liveness; (b)
    liveness-precise maps. (a) retains an object held only by a dead local until the function
    returns; (b) needs a liveness pass. Decision (maintainer, 2026-11-06): **(b), with liveness**: reference locals
    and operand slots are marked only where still live at the safepoint. The design:
    * *Where.* A pre-pass in the shared core, `jit/common/liveness.py`, beside `choose_pins`'s
      pre-pass (the code generation stays one pass, D26). It runs only for functions with a
      reference-typed local or a reference operand at a site, so reference-free code compiles as
      before; its output is one live set per site, the same for both architectures.
    * *Locals.* A backward pass over the function's instruction list with the live set as a
      Python int bitset over its reference locals: `local.get` adds, `local.set` and `local.tee`
      remove (`tee` reads its operand, not the local); at a block's `end` the set is the block's
      continuation; `br`, `br_if`, `br_table` take the target labels' sets (a block's end, a
      loop's header, the union for `br_if`/`br_table` with the fall-through); `return`,
      `unreachable`, `throw` and `throw_ref` outside a `try_table` give the empty set; a loop is
      iterated until its header set is stable (sets only grow; at most one pass per local and
      nesting level). **Exception edges:** inside a `try_table`, every call site and every
      `throw` also flows to each catch clause's label, so a local read in a handler is live at
      every call of the protected block. The set recorded at a call is the set after it, joined
      with the catch labels' sets.
    * *Operands.* An operand below a call is consumed by a later instruction; it is dead only when
      that consumer is `drop` (found by a stack simulation in the same pre-pass). A value that
      leaves its block through a branch or `end` counts as live (no tracking across labels).
    * *Nulling.* The walk writes null into each reference slot of the function (the per-function
      bitmap) that the site does not mark live. A dead slot is never read before it is written
      (that is what dead means), so nulling is safe, and afterwards every reference slot holds a
      valid word: invariant I3 holds for marked and unmarked slots alike. Without nulling, a dead
      slot would keep an offset into the old space, and a later over-marking error would make the
      collector read poison.
    * *Testing.* Unit tests of the live sets on hand-written functions; on the whole spec suite
      every live map is a subset of the full map; the whole suite and the fuzz seeds under stress
      and poison with the live maps. Mutations: a dropped live slot (a back edge, a catch edge,
      `tee` as a pure kill) must be caught by stress and poison (the nulled slot gives a null
      trap or a wrong value); marking a dead slot must pass every test (retention only, because of
      the nulling); marking a dead slot with the nulling removed must be caught by poison.
    * *Step.* A separate step 7, after the collector (step 5) and exceptions in the heap (step 6),
      not in step 3a: the full maps of steps 3a-6 are the oracle the live maps are checked
      against, and the stress and poison modes that catch a wrong live set exist only from step 5.
      Budget src ~220 (pass ~170, walk nulling and table ~50), tests ~220. Cost: the pre-pass
      only for functions with references; compile time recorded at step 7.
  * *Where maps are made.* In the shared core from the validator's operand types, identical for
    both architectures; the backends add two native numbers per site. Recommendation: as
    "JIT: safepoints and stack maps".
  * *How frames are found.* (a) a return-address walk: the bridge's exit record, per-site
    `ret_at`/`up`, the entry trampoline saving the enclosing record; (b) frame records written on
    the value stack at each call; (c) a frame-pointer chain on x86-64. (a) adds no instruction
    to a wasm-to-wasm call, about five to a host call and eight to an entry; it handles tail calls,
    cross-instance records, host thunks and nested entries without special cases in the code.
    (b) and (c) cost instructions on every call or a pool register. Recommendation: **(a)**.
    Against (c), Wasmtime's way: (a) depends on correct tables (step 3a's check mode verifies the
    walk on the whole suite), and native tools (`perf`, `gdb`) cannot unwind through JIT frames
    without a frame-pointer chain. Decision (maintainer, 2026-11-10): **(a)**; support for
    debuggers and profilers is recorded in ROADMAP.md (phase 6).
  * *Tables for every module.* Every frame of a store must be walkable, so every compiled module
    carries its site table, whatever its types (2.7-5.1 % of the code on today's modules).
    Decision (maintainer, 2026-11-06): approved.
  * *The four invariants* I1-I4 become a stated contract of the core, with tests and mutations;
    I1 ("references are never pinned") is the one ROADMAP's GC note asked for.
* **Q4 Where the collector runs.** (a) Python, in the allocation service; (b) the same algorithm
  as a wasm module, shipped as bytes, compiled by our own JIT for each architecture, entered from
  the service, with the roots gathered by Python (the walk) into a buffer the module rewrites.
  Measured copying: about 700 ns per live object in Python, 11.3 ns in wasm on `jit-x86_64`
  (Wasmtime 10.8 ns on the same WAT). The frame walk stays in Python (0.5 µs per frame).
  Recommendation: **(a) in step 5** (the oracle, about 420 lines), **(b) only as step 9**, if a
  benchmark shows collection time dominating. (b) is also how JIT-AS-WASM.md would port it:
  written once, architecture-free.
  Decision (maintainer, 2026-11-10, revised the same day after the review and the proposal
  GC-COLLECTOR-WAT): **(b) from step 5**, no Python collector. "An artifact built outside the
  package" is avoided by the shipping rule (the `.wat` source, the committed `.wasm`, a test that
  they match; "Roots and the collector"). The collector is atomic (no interrupt poll) and checked by
  an independent Python verifier (form and a graph digest before and after). Self-compilation is not
  a precondition: the module is compiled by our JIT like any module.
* **Q5 The context ABI and artifact change.** New in this revision: word 14 `EXIT_RECORD` in
  every context, the bridge and entry trampolines writing and saving the exit record, and the
  `STACKMAPS` section in every artifact; as before: the hidden memory's words, the GC group, codes
  16-18, the `externref` re-encoding. (a) amend v1 without a bump: no artifact file has been
  written (ARTIFACT.md part 2 is fixed by ROADMAP "Next" item 6, after this spec), as D34, D50
  and D52 did; the trampolines are the runtime's own, and no foreign host provides a bridge yet
  (the C loader of D36 does not exist). The hard rule's test becomes: a module compiled without a
  site table is refused at instantiation. (b) bump `ctx_abi_version` and `format_version` to 2
  with the refusal test of an old artifact. (b) is cleaner but bumps a version no file has ever
  carried. Recommendation: **(a)**, recorded as a new decision at step 3a, with the maintainer's
  approval as the hard rule's exception, and the artifact-format spec of item 6 writing the
  `STACKMAPS` section from its first version. Decision (maintainer, 2026-11-06): **(a)**, amend v1 without a version bump
  (word 14, the bridge and entry, the `STACKMAPS` section). Step 6's change of words 11-13 and of
  the `exnref` encoding follows from the Q7 decision and is recorded under the same amendment.
* **Q6 `pyc` representation.** (a) a struct as `[rtt, fields…]`, an array as `[rtt, data]`
  (`bytearray` for `i8`, a list otherwise), an i31 as an int, host values boxed when they enter
  the any hierarchy; (b) a `__slots__` class per type; (c) one generic object class. Measured
  allocation 30, 93 and 128 ns, field reads 12, 10.8 and 14.6 ns. (a) carries over to MicroPython
  unchanged (lists, `bytearray`, small ints). Recommendation: **(a)**. Unchanged by the copying
  decision: `pyc` uses Python's collector. Decision (maintainer, 2026-11-10): **(a)**.
* **Q7 Exception objects and GC.** (a) keep D52's arena as a precise root, scanned by tag at
  every collection (cost per collection grows with every reference-carrying exception ever thrown,
  none freed); (b) exception objects in the GC heap, as Wasmtime does (its `exnref` is a GC
  reference). Decision (maintainer, 2026-11-06): **(b)**, as its own step (step 6) right after the collector works.
  The design:
  * *Object.* A struct-like heap object of the tag's exception type: header, the tag identity
    (u64, the S0012 context word's value) at 8, the tag's parameters from 16 at their natural
    alignment. One type-info record per tag type (kind `exn`), naming the reference fields. An
    `exnref` is its u32 offset; null is 0.
  * *`throw`* becomes an allocation in the core (`common/gc.py`, the `struct.new` path): spill,
    bump, the service on a full semispace, header, identity, payload from the operand slots, then
    `throw_ref`'s tail (store the offset in the pending word, return 14). The slow path is a
    `call_host` site, so a `throw` is a safepoint whose map covers its payload operands and every
    live slot below them; a `throw` may collect. `throw_ref` allocates nothing.
  * *Landing pads.* `exn_match` reads the identity at `heap base + pending + 8`, `exn_field` a
    payload field at its offset, `exn_load` the offset itself (zero-extended u32). Between a
    `throw` and its pad or entry only epilogues run, so no collection happens while an exception
    is in flight; the pending word is a root as a defence (verify mode).
  * *Interface.* `throw` leaves the D39 backend interface (the core emits it from existing
    methods); `exn_match`, `exn_field` and `exn_load` change their bodies to read through the
    hidden memory (both backends, a D39 amendment of S0012's Q5 methods). Status 14 propagation,
    the `error` label and `landing` do not change.
  * *Stores without GC types.* A module with `throw`, `throw_ref` or `try_table` gets the hidden
    memory's words and the GC group (allocation service, one RTT word per tag type it throws); the
    store's heap is reserved with the first such instance (virtual space and the header page) and
